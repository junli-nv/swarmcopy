# v0.7.0：调度、本地复制与完成统计

[English](OPTIMIZATION-0.7.0.en.md) · [示例](EXAMPLES.zh-CN.md) · [开发指南](DEVELOPMENT.zh-CN.md) · [可复核数据](optimization-0.7.0-results.json)

## 本次结论

九节点、每节点全新接收 32 GiB 的固定并发对照中，0.6.0 分发阶段均值 32.39 秒，0.7.0 为 25.10 秒，耗时减少 **22.50%**；包括部署和收尾的控制器总耗时均值 39.68 → 31.61 秒，减少 **20.34%**。源所在节点的目标文件改为本地读取、验块、写入，不再经网络绕回。自适应继续默认关闭，TCP 继续默认启用。

这是指定集群上的组合优化结果，不能分解为每项改动各自的贡献，也不能保证 484 GiB 文件或其他规模有同样百分比。首次读取来源建立摘要仍需时间；来源未变时可复用指纹绑定的摘要缓存。

## 为什么改这些

已完成的约 484 GiB chunks 作业没有最终整文件回读，逐节点 FileHashBytes/FinalHashSeconds 都是零，不能再把它的分发耗时归因于最终校验。检查发现两处可直接改善的工作：每次选块持全局锁遍历大量缺块并逐一评价来源；源所在节点的目标副本又通过其他节点收回了大量数据。阶段内并发工作时间是累计值，不等于串行耗时；没有同期磁盘和网卡利用率证据，不能断言磁盘或网络已经跑满。

## 实现及不变量

- `adaptive.go` 对一次范围选择最多评分 255 个缺块候选，以随机起点和互素步长覆盖整个范围，不固定只看前 255 块；来源数为 1 时提前返回。若抽样未找到可下载块，扫描合格来源的可用位图补选一个，避免稀疏来源让 worker 空闲。最多记录 256 个评分候选，但位图检查仍可能遍历全范围；并非所有调度工作都变成常数时间。
- 这是近似稀缺块选择，不保证找到全局最稀缺块。保留来源并发上限、过期来源过滤、流水窗口优先、endgame 与失败重试规则。新增 SchedulerCalls/Candidates/WorkSeconds，便于后续测量锁内工作。
- 源所在节点且列入目标时，peer 按可信来源布局只读本地源文件，优先复制到自己的目标暂存；其他节点仍按 TCP/QUIC 获取已验证块。保留逐块摘要、full 模式最终校验、fsync 和原子发布，不依赖大小判定完整，不使用未经校验的 reflink/硬链接捷径。来源变化或读写失败按本地错误处理。
- 不可变清单的 ID 在节点构造时缓存，状态/发现请求复用，避免反复在锁内编码并哈希清单。不改 SCDP/1、旧清单 ID 或摘要算法。
- Downloaded/ReceivedBytes 只记网络；LocalCopied/LocalCopiedBytes 单列本地复制。From 的 local-source 单列来源；全局进度仍按已验证目标字节计算。下载限速也约束本地复制读取。
- agent 检查启动版本，升级时重启旧 peer，但仍验证并复用已有暂存，不无条件丢弃缓存或数据。

## 完成摘要怎么读

成功后打印 JOB SUMMARY 并保存 result.json 的 Summary：本次总耗时、准备耗时、分发/校验/收尾耗时、完成节点数、网络/本地复制/复用字节、集群平均接收速度和接收节点平均速度的中位数。

集群平均速度 = 本次新增的对应字节 / 本次控制器总耗时，**包含准备时间**。续传时已有 peer 可能在准备阶段继续传输，分母必须覆盖同一时间窗口。它是所有目标的合计，不是单节点速度，也不是网卡线速。单节点速度中位数使用各自传输阶段时间，排除没有新网络接收的节点。

续传观察同一 peer 实例时扣除调用前已有计数；peer 重启则用新实例计数，已有验证数据列为复用，不把历史数据当本次新流量。采样不是原子集群快照，准备和分发计时以控制器阶段边界为准，少量早启动 peer 的工作可与准备重叠。旧版本没有 Summary 的结果只显示原有记录，不编造历史耗时。完成后 `watch --job ID` 显示文本摘要；`status --job ID` 的 JSON 包含 Summary，保持机器可读。

## 公平对照与限制

2026-11-16，同一九台 x86_64 节点；32 GiB 固定只读来源；chunks/BLAKE3；TCP；workers/uploads=4/4；不限速；自适应关闭。每轮使用从未存在的目标目录，在全部九节点 sync 并 drop_caches=3，确认机器身份不同。来源清单先生成，各计时轮均验证缓存复用。运行中重试正常计入，未用续传结果测速。每轮结束再独立 SHA256 检查所有九份成品，校验时间不计入传输时间。

| 运行顺序 | 版本 | 最慢节点分发阶段（秒） | 控制器总耗时（秒） |
| --- | --- | ---: | ---: |
| baseline-2 | 0.6.0 | 31.865 | 38.730 |
| candidate-final-1 | 0.7.0 传输构建 | 24.429 | 30.448 |
| candidate-final-2 | 同上 | 25.766 | 32.767 |
| baseline-final-2 | 0.6.0 | 32.905 | 40.625 |
| candidate-release-1（发布物追加验证） | 0.7.0 最终构建 | 25.223 | 32.723 |

阶段定义为各节点 TransferSeconds + FinalSyncSeconds + PublishSeconds 之和的最大值；不包含首次源摘要生成。控制器总耗时由外部单调时钟计量，含 SSH 部署/启动/结束，排除建立测试源和事后独立校验。旧版网络合计 288 GiB（包含源节点回环/接收），新版网络 256 GiB + 本地 32 GiB，最终目标副本完全相同。这项行为改进是优化的一部分，不能据此声称纯网络协议本身快了 22.5%。

平衡顺序测量后仅调整了完成统计与显示；最终二进制又从零追加验证一轮。JSON 保留构建 SHA256、前期探索轮次和所有独立检查计数，未将不同候选混合算均值，也未挑选最快单轮作为收益。这里的源缓存复用和页面缓存清理分别说明，不能把“冷缓存”理解成每次重新生成来源清单。

## 验证与继续优化

通过 Go race 测试、vet、英文 CLI 帮助检查、真实进程链中断/损坏修复；三节点 QUIC/full 验证（包含完整文件摘要、本地副本网络接收为零）、本地复制部分完成后 Ctrl+C/同 ID 续传、保存后的 status/watch 摘要检查。全部实机成品另经 SHA256 复核。Linux x86_64 已实机运行；aarch64 为静态交叉构建，未在 ARM 实机验证。

复现时冻结两个构建及来源，先独立记录来源摘要，预热并验证来源清单缓存；按 B-A-A-B 顺序分配全新目标，逐轮清缓存，串行运行、记录所有成功/失败和重试，所有目标完整后独立校验；不要在测速期间同时跑 CPU 微基准。固定并发示例见 EXAMPLES。后续按 SchedulerWorkSeconds、锁等待、磁盘和 NIC 同期采样再决定是否改批量 I/O 或并发；不要默认开启自适应来掩盖锁内开销。
