## 如何保证新起点和校验可信

每个方法、每轮使用独立 UUID 目录；157 个节点全部通过目录不存在检查，随后 sync、drop_caches=3 成功，合计 942 次节点缓存屏障。三轮次序为 rsync→SCDP、SCDP→rsync、rsync→SCDP。两种方法均不限速，预先准备种子及初始导入不计时；每个方法开始前检查程序和两架构部署文件摘要未改变。传输期间允许正常重传与恢复，计时不重置。

每轮 rsync 的 156 个接收节点均通过完整 SHA-256，保留各次尝试的 literal bytes、transferred file bytes 与退出码。每个节点复制后立即校验，校验可以在节点之间重叠。SCDP 三轮接收节点全部 Origin=false、Downloaded 等于完整文件大小、Complete=true，总有效下载量恰为文件大小乘 156；每个新接收文件都经过整文件 SHA-256 与 fsync。SCDP 时间还包含程序部署及本任务做种进程停止。

测试结束后，独立检查 157 个不同的内核 boot ID，排除重复主机别名；逐台检查 3 个任务共 471 个拥有身份的进程记录，全部已停止。实际节点、UUID、PID 和完整日志只保留在控制端私有 run/ 目录。

## 源节点负担

每轮 SCDP 从初始种子接受的有效块合计为 47.10, 46.83, 47.68 GiB；单源完整分发的有效文件量为 5838.83 GiB。有效来源字节减少范围 99.18%–99.20%。这是接收端有效块来源统计，不是完整网卡计数，不含被丢弃重传和协议开销。

## 适用边界

所有实测节点均为 x86_64，116 个 XFS、41 个 ext4，使用本地 RAID。种子出口是四个 100 Gb/s 端口组成的 LACP bond；两种方法使用相同源节点、普通系统路由，未使用原生 RDMA。

这是用户现有 rsync-over-SSH 方案与 SCDP-over-HTTP 的整体方案对比：SSH 加密，HTTP 明文，不能把全部收益都归因于 P2P 拓扑。冷的是 OS 页缓存，磁盘/控制器缓存未清，后台负载未隔离；rsync 的最终 SHA-256 表示读取内容正确，未额外承诺与 SCDP 相同的断电持久化语义。三轮不是所有网络与集群的性能保证，也不证明节点越多必然越快。早期 5/45 节点结果没有清缓存，不能与本表拼成严格的规模曲线。
