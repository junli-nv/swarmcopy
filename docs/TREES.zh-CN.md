# 多文件与目录：设计及验证

[English](TREES.en.md) · [示例](EXAMPLES.zh-CN.md) · [开发指南](DEVELOPMENT.zh-CN.md) · [文档索引](README.md)

## 数据模型与布局

新建 distribute --source 对单文件和多文件统一使用树清单：SHA256 组合可用 v2，自定义摘要和默认 chunks/BLAKE3 使用 v3。v1 单文件清单的字段编码、ID 与 prepare/seed-file 工作流保持兼容。

Entries 按相对路径字节顺序排序，含 Path、Kind（file/dir）、Size、Mode（普通 0777）、Modified（Unix 纳秒）。v2 普通文件含 SHA256；v3 用 Digest 保存算法名与摘要。目录保留 basename，多个顶层文件直接放在 dest，Name 固定为 files，不增加批次根目录。

普通文件按 Entries 顺序组成逻辑字节流。Size 为普通文件大小之和；默认 16 MiB 分块，摘要算法由清单绑定，尾块可更短，块可跨文件。目录与空文件不占逻辑数据字节，但必须在清单中。

v2/v3 的 Manifest.SHA256 是 Entries JSON 的 SHA256 树摘要，绑定元数据及各文件摘要，不是裸字节拼接内容摘要。v2 文件 SHA256 可用 sha256sum 独立核对；v3 应使用清单声明的算法。Manifest ID 是完整清单 JSON 的 SHA256，还绑定算法及分块边界/摘要。

full 的 treeHash 按顺序消费逻辑字节，并按文件边界验证对应算法摘要；全部文件通过后才返回可信树摘要。默认 chunks 使用强块摘要，不执行最终整文件内容复核，不能把两种模式的门槛混为一谈。空数据集同样需走完成和发布检查。

## 控制器流程

1. 展开 repeatable source、位置参数和 glob，递归构建固定来源列表；拒绝同名根、重叠根、符号链接及特殊文件。
2. 建立来源清单，并检查文件身份／大小／mtime／ctime、权限和目录成员在哈希前后未变。没有变化可复用本地来源缓存；recheck 强制读盘。
3. SSH 部署同一个二进制，向每个节点上传可信清单，执行 tree-check 盘点成品。
4. 若有普通文件内容冲突，控制端按 existing 策略处理。ask 列出冲突并通过 /dev/tty 询问一次；脚本需显式选择。此时尚未发布新数据。
5. 控制器在目标列表时直接只读供种，同路径本机目标复用成品，异路径本机目标本地复制。否则，若已有完整副本，跳过初始介质导入，该副本直接成为来源；选定 seed 本身可以缺文件。否则通过 SSH 向 seed 导入一次。
6. 初始导入仅用 Go archive/tar 的内存流，种子直接形成各个普通文件，没有完整 tar 中间件。结束标记仅在来源快照复查成功后写出；不完整流不发布数据。
7. 全体 peer 共享既有分块调度、TCP/QUIC、上传限流、流水校验与全局监控。原子保存结果后按归属停止进程并清理部署/空暂存（keep-seeding 除外）。

首次新来源可能需要控制端额外的一次完整哈希读取；导入时 seed 独立复核摘要。后续来源缓存减少重复读盘。该成本不能从新版本总耗时中隐去，也不能把历史 prepared-seed 单文件测速直接宣称为本版本端到端成绩。

## 节点存储与恢复

contentFile 抽象保留 ReadAt/WriteAt/Sync 等接口，v1 使用 os.File，v2/v3 使用 treeStore。treeStore 用排序偏移二分定位文件，ReadAt/WriteAt 自动跨文件边界。每个活动文件跨度临时打开描述符，避免与文件总数成正比的常驻 FD。

新暂存位于 `dest/.swarmcopy/trees/<manifest-id>/data/<relative-path>`，与成品同盘；旧 .swarmcopy-trees 按需原位恢复。重新检查已有块，只把通过清单绑定摘要的数据记为 Have；能证明未写入的稀疏空洞可直接视为缺块。成功后按归属清理，见[清理规则](CLEANUP.zh-CN.md)。

已有成品经过清单绑定的逐文件摘要 或可信元数据缓存匹配后可直接参与做种。resume 策略将冲突旧文件复制到独立暂存文件，再检验全局块，绝不原地覆盖旧成品；replace 不拷贝冲突旧文件，但仍保留同任务已完成临时块。已经匹配的文件不会因为 replace 被重新下载。

多个文件共用块意味着：缺一个小文件时，其跨界块可能包含已有邻接文件的部分字节；写入遇到已发布文件只比较内容，不修改它。不是每个文件一个独立下载任务。

## 发布与崩溃一致性

完成顺序：数据 fsync → 所选模式门槛（chunks 全部强块已验；full 另行完成逐文件摘要）→ 逐文件发布 → 目录元数据/父目录 fsync → Complete。full 摘要可以在接收阶段流水进行。

新文件用 link/unlink 做不覆盖发布；已授权冲突文件在复查旧指纹后 rename 替换。发现目标在处理期间发生变化时拒绝已检测到的修改，要求外部写入者与任务互斥。每文件原子，不是整个集合原子；发布中断保留已完成文件，下一次复用并继续。

特别处理 link 成功、unlink 前崩溃的情况：若暂存文件 link count > 1，恢复写入前复制脱离原 inode，保证后续修复不会通过硬链接修改旧成品。权限／时间戳在文件 fsync 前设置；目录逆序应用元数据。

目标额外文件不会被删除。匹配文件保持原有元数据，新文件保存普通权限及 mtime，目录应用源元数据。UID/GID、ACL、xattr、符号链接、硬链接拓扑及稀疏布局不在当前支持范围。

## 路径、并发与缓存边界

所有内容路径必须是清理后的相对路径，不能有 ..、绝对路径、NUL、反斜线、重复／缺失父目录或 .swarmcopy 保留前缀。限制 100,000 项、1,000,000 块，沿用清单读取大小上限。使用 os.Root 限制访问范围，并逐层拒绝目标／暂存符号链接和非目录祖先。

同一个 dest 的 peer/import 使用排他 flock；上传与发布用 treeStore 的 RWMutex 协调。已有文件不可被其他应用并行改写；缓存不是对恶意本机管理员或修改中的文件系统的安全承诺。

来源缓存绑定冻结路径、元数据与 Linux 指纹。目标固定 `.swarmcopy/cache.json` 只保留最近清单 ID 的逐文件 device/inode/size/mtime/ctime；不依赖目录 mtime。旧 verified.json 可按需兼容读取。缓存原子替换，--recheck 强制内容检查；chunks 新下载成品不会因此获得 full 缓存。

## 历史多文件功能验证（v0.4.0）

五个 x86_64 真实计算节点，139,460,641 字节，5 个文件、7 个条目（含空文件／空目录），16MiB 分块；每轮都用独立逐文件 SHA256 再核对五台节点。这是功能验证，**不是冷缓存测速对照**。

| 场景 | 全体节点新增介质下载字节 | 结果 |
| --- | ---: | --- |
| 全新 TCP 分发 | 557,842,564 | 4 个接收节点全量，种子 SSH 导入 |
| 3 台完整，2 台缺失，指定 seed 也缺 | 173,015,073 | 3 台下载 0，跳过头结点介质上传 |
| 5 台全部完整 | 0 | 直接复用 |
| 1 台损坏一个分块，resume | 16,777,216 | 只重新下载坏块 |
| 1 台同名损坏，replace | 38,797,345 | 重新接收该文件跨越的块 |
| 全新 QUIC 分发 | 557,842,564 | 同程序 UDP 数据通道 |
| stop 后同 job ID 恢复 | 520,093,696（恢复阶段） | 保留已验证块，最终全体一致 |

恢复实验在接收端已有 5,242,913 字节完整分块时执行 stop；初次与恢复两阶段的网络计数不可当成“从零测速”。各案例完成后均停止了所属 peer。

自动测试覆盖 v1 ID 不变、跨文件乱序接收、块与逐文件摘要双重门槛、完整文件复用、缓存失效、空目录／零字节集合、源变化、路径穿越、符号链接、并发目标变化、冲突修复／替换、发布中断恢复、硬链接崩溃恢复及实际 TCP/UDP 数据传输。使用 race 检测；aarch64 仅交叉构建，未做硬件测试。

上表来自当时的开发过程的功能构建。最终候选 x86_64 SHA256 为 003a378c0fd4859cb085e67c100329f768d649e0ab6622389ea7f80b10bde5bb，另外完成全新 TCP、8 并发 QUIC 各一轮（各 557,842,564 下载字节），以及真实控制终端默认 ask→r 的一块修复（16,777,216 字节）。其余崩溃和兼容边界由最终代码 race 测试覆盖，不声称上表每项都在最终二进制重复执行。

## 后续优化方向

优先对大量小文件进行独立元数据和 FD 开销 profiling，再决定描述符池或按文件边界打包小块；不要因缓存过度省略数据验证。可考虑按文件完整性组合多个部分来源以避免“无单个完整副本但全体覆盖数据”时的初始导入，以及初始 SSH 阶段的块级续传。

新增传输策略统一在 main 和同一二进制内用显式选项控制。新的性能结论必须使用同一硬件、相同清单、全新目标和一致缓存条件，区分导入、盘点、传输、哈希、fsync、发布和部署，不以本表功能案例作为加速倍数。
